## 2. Incident narrative

Asterion Research Systems (incident ARS-2026-041) detected unusual outbound
DNS activity from its research network around 2026-10-28 14:00 IST, shortly
after an unexpected repository export event. A workstation appears to have
tunneled a confidential research briefing out of the organization through DNS
queries to `sync.ghostwire.test`. The endpoint investigation was interrupted;
participants must reconstruct the incident from preserved evidence.

## 3. Fictional network (deterministic)

| Component | IP | MAC | Hostname |
|---|---|---|---|
| Compromised research workstation | 10.40.2.17 | `6a:8c:47:2d:91:b3` | ARS-WS-RES-07 |
| Finance workstation (benign) | 10.40.2.21 | `3e:f1:a9:74:0c:5a` | ARS-WS-FIN-03 |
| DNS resolver | 10.40.0.53 | `5a:2d:e8:11:6f:90` | ars-dns-01 |
| Repository server | 10.40.1.20 | `0a:9b:c3:7e:42:d1` | ars-repo-01 |
| Gateway | 10.40.0.1 | `22:9a:f0:c4:18:77` | — |
| External exfil domain | sync.ghostwire.test | — | — |

All MAC addresses are locally administered unicast (2nd bit of octet 0 set,
multicast bit clear), so they never collide with a real vendor OUI. IPs use the
documentation range 10.40.x.x; the domain uses the reserved `.test` TLD.

A *prior* lease exists for the compromised IP `10.40.2.17` with a *different*
MAC (`12:7e:c4:88:0a:1f`) on 2026-10-20. This forces participants to pick the
lease active *during the incident* rather than blindly trusting any lease that
mentions the IP.

## 4. Evidence files

Four participant-facing files (under `evidence/`):

- `network_capture.pcap` — pcap with Ethernet headers preserved, ~187 frames,
  ~21 KiB. Contains benign DNS/ARP/HTTP background traffic from several hosts
  plus the suspicious DNS sequence from the compromised workstation.
- `dns_resolver.log` — 89 DNS events (timestamps, src IP, qname, qtype,
  rcode+name, answer). 37 are to `sync.ghostwire.test` (34 data segments + 3
  control queries `init`/`ping`/`done`).
- `dhcp_leases.csv` — lease history including the prior/expired and the active
  lease for the compromised IP.
- `repository_audit.log` — repository access log; the incident event is the
  `export` of `research/chimera/chimera_phase2_briefing.md` by user `res07`
  from `10.40.2.17` at 14:02:17 IST.

All four sources agree on the same timeline (same IST datetimes; the pcap
stores Unix epoch seconds derived from those datetimes).

## 5. Payload encoding

- Scheme: Base64URL (RFC 4648 URL-safe alphabet), padding stripped.
- The exfiltrated artifact is wrapped in a small `ARS-EXFIL/1` envelope that
  carries `artifact_id`, `filename`, and a `content_sha256` integrity tag, so
  reconstruction can be validated without any external service.
- Envelope bytes → Base64URL → split into 48-char chunks.
- Each chunk becomes the second label of a DNS query:
  `segNNN.<chunk>.sync.ghostwire.test`, where `NNN` is a 3-digit zero-padded
  sequence identifier (the ordering key).
- Label length ≤ 48 (well under the 63-byte DNS limit); full qname ≤ 75 chars
  (well under 253). 34 segments total.
- Control (non-data) queries `init.`, `ping.`, `done.` mark tunnel
  handshake/keepalive/close and do NOT match the `segNNN` pattern, so
  participants must filter to data-bearing queries only.

## 6. Flags

- Flag 1: `VVVFLAG{<compromised_mac>}` — derived from the compromised
  workstation's MAC (`6a:8c:47:2d:91:b3`). Recovered by MAC attribution
  (pcap Ethernet source ↔ active DHCP lease).
- Flag 2: a unique token embedded inside the recovered artifact's restricted-
  asset section. The token is generated at implementation time and stored only
  in `organizer/flag_config.json` (generated by `generate_evidence.py`,
  organizer-only). The flag token differs from the audit-log resource name,
  so the audit log alone is not a shortcut to Flag 2 — the DNS payload must
  actually be reconstructed and decoded.

Authoritative values live in `organizer/flag_config.json`, generated by
`organizer/generate_evidence.py` (the single source of truth). The official
solve and tests independently derive both flags from the evidence and assert
equality with that file.

## 7. Intended investigation path

1. Establish the incident window (resolver log / pcap).
2. Spot the unusual `sync.ghostwire.test` queries with long encoded labels.
3. Attribute the source: pcap Ethernet src MAC ↔ DHCP lease active during the
   window. → Flag 1.
4. Correlate repository audit: the same host exported the artifact just before
   the DNS burst.
5. Reconstruct the payload: extract `segNNN.<chunk>` labels, order by `NNN`,
   concatenate chunks.
6. Decode: restore Base64URL padding, decode, validate the envelope's
   `content_sha256`. → Flag 2.

## 8. Determinism & reproducibility

- Fixed seed (`20261028`); no real DNS queries; no network access at generate
  time.
- `generate_evidence.py` writes a `_manifest.json` consumed by
  `generate_capture.py` so the pcap reproduces the exact DNS events in the
  resolver log.
- Re-running the generators produces byte-identical evidence and pcap.

## 9. Deviations from the spec

None. The implementation follows the approved design. The only environment
constraint surfaced during implementation: the build sandbox has **no Docker**,
so docker-compose could not be exercised here; `tests/smoke.sh` runs the
generate→solve→test pipeline instead, and the portal was verified by running
`portal/app.py` directly and curling every route (see the completion report in
`docs/deployment.md`).
